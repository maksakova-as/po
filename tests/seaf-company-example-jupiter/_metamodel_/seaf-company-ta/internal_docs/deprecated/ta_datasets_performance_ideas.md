# Идеи ускорения TA-датасетов

Документ-черновик по результатам обзора метамодели TA и цепочек reverse. 

## Наблюдения и вероятные узкие места
- В `/_metamodel_/seaf-company-ta/ta/datasets.yaml` одинаковый блок конфигурации вычисляется во многих датасетах.
- Reverse-датасеты вызываются через `$eval(...)` даже когда reverse отключён или не выбран приоритетом.
- В reverse-частях много перекрёстных `$eval` (networks/servers/components/gateways), что порождает повторные вычисления.
- `seaf.company.ds.ta.all_objects` делает большой merge и часто используется как fallback в UI.

## Быстрые улучшения (низкий риск)
1) Ленивая генерация источников
   - Вычислять `seaf1` и `reverse` только если источник включён.
   - Не вызывать `$eval` для reverse, если источник отключён или не нужен по приоритету.

2) Общий датасет с конфигами
   - Добавить `seaf.company.ds.ta._config`, который отдаёт `enabled` и `priority`.
   - Использовать его через `origin`, чтобы не повторять разбор конфигов в каждой витрине.

3) Заменить `$eval` на `origin` там, где возможно
   - Явные зависимости через `origin` позволяют кэшировать результаты и избежать повторной оценки.

## Средние изменения (заметный выигрыш)
4) Стабилизировать цепочки reverse
   - Ввести базовые reverse-датасеты (например `...networks_base`, `...servers_base`).
   - Производные reverse-датасеты используют базовые через `origin`.
   - Особенно важно для `logical_links`, `storage`, `elb/nat/vpn`.

5) Сократить использование `all_objects` как fallback
   - Перейти на более узкие fallback-датасеты по сущностям.
   - Использовать `all_objects` только там, где реально нужен «всё-в-одном».

6) Уменьшить `$spread() + $merge()` на больших списках
   - По возможности заменить на одно-проходные `$reduce`.

## Стратегическая модернизация
7) Слои raw -> normalized -> view
   - `raw`: загрузка SEAF2/SEAF1/reverse без тяжёлых трансформаций.
   - `normalized`: нормализация ID и построение ссылок.
   - `view`: финальные датасеты для UI.
   - Это уменьшает повторные вычисления и повышает переиспользуемость.

8) Материализация тяжёлых reverse-датасетов (если платформа позволяет)
   - Предрасчёт и хранение результатов для самых тяжёлых reverse-частей.

9) Профилирование и метрики
   - Фиксировать время выполнения через `/core/storage/jsonata/<dataset_id>` для ключевых витрин.
   - Сравнивать «до/после» при каждом изменении.

## Детальный план модернизации по фазам

### Фаза 0: Бейзлайн и профилирование (1-2 дня)
- Измерить время для ключевых датасетов через `/core/storage/jsonata/<dataset_id>`:
  - `seaf.company.ds.ta.{dcs,dc_regions,dc_azs,networks,network_segments,servers,storages,k8s,all_objects}`
  - `reverse2seaf2.ds.ta.reverse.{servers,networks,network_components,nat_gateways,vpn_gateways,elb_network_components,logical_links}`
- Зафиксировать суммарное время загрузки 2-3 «тяжёлых» UI-страниц.
- Сохранить результаты в таблицу (dataset_id -> time_ms).

### Фаза 1: Снижение дублирования в TA-датасетах (низкий риск, быстрый эффект)
1) Общий датасет с конфигами
   - Добавить `seaf.company.ds.ta._config` в `/_metamodel_/seaf-company-ta/ta/datasets.yaml`.
   - Он отдаёт `{ enabled: [...], priority: [...] }` и производные флаги.
   - В остальных датасетах заменить локальный `$ta_config` на `origin: { cfg: seaf.company.ds.ta._config }`.

2) Условная генерация seaf1/reverse
   - Обернуть `seaf1`/`reverse` блоки проверками по `cfg.enabled`.
   - Не вызывать `$eval` для reverse, если reverse выключен или не используется.

3) Переход от `$eval` к `origin`
   - Там, где датасет тянет другой датасет, задать явный `origin`.
   - В `source` использовать переменные `origin`, а не `$eval(datasets."...".source)`.

Ожидаемый эффект: меньше повторной обработки конфигов и тяжёлых reverse-вызовов.

### Фаза 2: Нормализация reverse-цепочек и повторное использование вычислений (средняя сложность)
1) Разделить тяжёлые reverse-датасеты на base + derived
   - Примеры: `reverse2seaf2.ds.ta.reverse.networks_base`, `...servers_base`.
   - Base-датасеты формируют общие индексы и нормализованные данные.
   - Derived-датасеты берут base через `origin`.

2) Общие lookup-индексы для reverse
   - Создать `reverse2seaf2.ds.ta.reverse._indexes`:
     - subnet_id -> subnet object
     - vpc_id -> network_component
     - az -> dc mapping (если нужно)
   - Использовать их в logical_links/storage/network_components.

3) Унифицировать вспомогательные функции
   - Вынести `$normalize`, `$to_list`, `$first_id` в общий `reverse._utils` датасет.

Ожидаемый эффект: меньше рекурсивных вычислений, меньше повторов.

### Фаза 3: Замена `all_objects` и сужение UI-зависимостей (средний/высокий эффект)
1) Узкие fallback-датасеты
   - Например `seaf.company.ds.ta.fallback.networks` (только networks и зависимости).
   - В UI заменить `all_objects` на узкие fallback-датасеты.

2) Обновить presentations/widgets
   - Использовать `all_objects` только там, где действительно нужен «универсальный» источник.
   - В остальных местах достаточно `seaf.ds.objects` + конкретный TA-датасет.

Ожидаемый эффект: избежать пересборки большого merge на каждом UI-вью.

### Фаза 4: Слои raw -> normalized -> view
1) Raw слой
   - `seaf.company.ds.ta.raw.*` для первичной загрузки.
2) Normalized слой
   - `seaf.company.ds.ta.norm.*` для нормализации ссылок.
3) View слой
   - `seaf.company.ds.ta.*` только для UI.

### Фаза 5: Материализация / кеширование (если платформа позволяет)
- Предрасчёт тяжёлых reverse-датасетов (servers, networks, logical_links, storage).
- Хранение результатов в стабильных датасетах, чтобы не пересчитывать при каждом запросе.

## Риски и меры
- Риск: изменения в порядке merge или источниках.
  - Мера: не менять приоритеты merge, добавлять тесты/сверки.
- Риск: скрытая зависимость UI от `all_objects`.
  - Мера: аудит ссылок `origin`/`datasets` в presentations/widgets.

## Стратегия внедрения
1) Внедрить Фазу 1 и измерить эффект.
2) Перейти к Фазе 2 для самых тяжёлых reverse-датасетов.
3) Заменить `all_objects` в 1-2 карточках UI и проверить поведение.
4) Постепенно перейти к слоистой архитектуре для самых дорогих сущностей.
