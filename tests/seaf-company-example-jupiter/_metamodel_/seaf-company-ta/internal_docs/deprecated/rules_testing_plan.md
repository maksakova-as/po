# План тестирования правил TA
## Алгоритм проверки правила
1. Открыть YAML с правилом и определить требуемые сущности/поля.
2. Выбрать минимальный набор данных для проверки и подготовить две версии:
   - **Позитивная**: данные удовлетворяют условию и правило не должно выдавать отклонения.
   - **Негативная**: данные нарушают условие, чтобы правило выдало отклонение (например, неверный `*_ref`, пустое поле и т.д.).
3. Внести нужную версию данных в соответствующий YAML, сохранить файл.
4. После любых правок перезапускать backend (см. `Docs/operations_manual.md`).
5. Запросить `curl -s http://localhost:8080/core/storage/problems/` и убедиться, что:
   - Найденный `id` совпадает с ключом в `_metamodel_/seaf-company-ta/rules/...` внутри секции `rules.validators`, а `uid` из `items` берётся отсюда же.
   - Для негативного сценария `items` появляется с ожидаемым `uid`, а для позитивного сценария — исчезает.
   - Чтобы отфильтровать только нужные записи, используй `curl -s http://localhost:8080/core/storage/problems/ | rg "seaf.validation.ta.components.server_existence"` или `Invoke-RestMethod http://localhost:8080/core/storage/problems/ | ? { $_.id -eq '...' }`, а затем по `items[].uid` (`rg`, `Select-String`, `Where-Object`) смотри, какой конкретно `uid` возвращается.
   - Зафиксируй, в каких файлах архитектуры (`architecture/ta/...`, `*_disabled`, `*_test`) ты менял данные и какие команды (`docker restart archtool`, `curl`, `Invoke-RestMethod`) выполнял, чтобы встроить это в отчёт.
Дополнительно: в rules.validators (_metamodel_/seaf-company-ta/rules/...) смотрите на id/uid, а вывод curl/Invoke-RestMethod фильтруйте через rg/Where-Object и упоминайте, какие items/uid появлялись в позитивном и негативном прогоне.

6. Проведи позитивный и негативный сценарии (включи/выключи соответствующие `architecture/ta/...`, `_disabled` или `_test` файлы), каждый раз перезапуская backend (см. `Docs/operations_manual.md`) и повторно проверяя `/core/storage/problems/`, чтобы увидеть появление и исчезновение `items`.
7. В таблице статусов укажи, какие файлы редактировались, какие команды и фильтры (`curl`/`rg`/`Invoke-RestMethod`) ты применял, и отмечай правило как `done` только после удачного позитивного прогонка.

### Быстрый доступ к ошибкам
Если нужно быстро посмотреть, какие ошибки по конкретному правилу уже зафиксированы, используйте например:

```bash
curl -s http://localhost:8080/core/storage/problems/ | rg "seaf.validation.ta.services.dc_existence"
```

или в PowerShell так, чтобы сразу получить нужный `id` и `items`:

```powershell
Invoke-RestMethod http://localhost:8080/core/storage/problems/ |
  Where-Object { $_.id -eq 'seaf.validation.ta.services.dc_region_existence' } |
  ConvertTo-Json -Depth 4
```

В этих командах вы легко увидите, появились ли нужные `items[].uid`, и что конкретно предлагает `correction`. Описание `rules.validators` подскажет, какой `id` и `uid` ожидаются для каждого правила.

### Как выбрать `id` и `uid`

1. Используйте `rg -n "rules.validators" _metamodel_/seaf-company-ta/rules` или `rg -n "seaf.validation.ta" Docs/rules_testing_plan.md` чтобы получить актуальный `id` и путь к `rules.validators` в `_metamodel_`.
2. Перед каждой проверкой перезапускайте backend (см. `Docs/operations_manual.md`).
3. Для быстрого доступа к описанию всех КБ-сервисов воспользуйтесь `http://127.0.0.1:8080/entities/seaf.ta.services.kbs/list` — там уже перечислены все `jupiter.kb.*`, и у каждого есть свои `protected_services`.
4. Отфильтруйте конкретный элемент так:

   ```powershell
   curl.exe -s http://localhost:8080/core/storage/problems/ |
     ConvertFrom-Json |
     Where-Object { $_.id -eq 'seaf.validation.ta.p3.k8s_policy_engine' } |
     ConvertTo-Json -Depth 5
   ```

5. В полученном JSON см. `items[].uid`, `deviation_id` и `description` — именно их удобно переносить в разделы `Notes` или отдельные списки доказательств.
6. Если вы предпочитаете `rg`/`Select-String`, оборачивайте команды в кодовые блоки и заменяйте пайпы на `&#124;`, чтобы они не ломали таблицу.

### K8s-проверки с `done_skipped_due_to_environmental_issues`
Qiesen правила (`seaf.validation.ta.p3.*`) теперь завязаны на сервисы КБ (`seaf.ta.services.kbs`), поэтому при повторной проверке:
1. Изучите JSONata в `_metamodel_/seaf-company-ta/rules/p3/` — т.е. `p3_k8s_allowed_registries.yaml`, `p3_k8s_policy_engine.yaml`, `p3_k8s_pam.yaml` и т.д. Ниже добавлен список `id`/`uid`, которые должны появляться, и `deviation_id` с `tag`/`registries`.
2. Откройте `_metamodel_/seaf-company-ta/services/kb.yaml`: там описаны допустимые `tag` (Repo/Registry/Policy/Scan/...) и обязательные поля (`technology`, `software_name`, `status`, `network_connection`). Именно эти свойства участвуют в проверке «KB -> K8s/cluster/compute».
3. Для негативного сценария временно удаляйте или корректируйте `seaf.ta.services.kbs` (например, уберите `tag=Registry` или `protected_services`) и перезапускайте `docker restart archtool` → `curl -s http://localhost:8080/core/storage/problems/ | rg "<rule id>"`. Для позитивного — возвращайте корректные значения и повторяйте.
4. Если какая-то зависимость тяжело реализуема (например, отсутствует тестовый кластер или атрибут `protected_services`), добавьте примечание в строку таблицы `Notes`, сохранив `done_skipped_due_to_environmental_issues`. После устранения ограничений можно вернуться к этим правилам.

### KB-ориентированные P3-проверки: что видно на стороне KB

- В `_metamodel_/seaf-company-ta/services/kb.yaml` перечислены допустимые `tag` (`Repo`, `Registry`, `Policy`, `Log`, `IdP`, `IdM`, `PAM`, `Secrets`, `CMC`) и обязательные поля (`technology`, `software_name`, `status`, `network_connection`), на которые опираются проверки `seaf.validation.ta.p3.*`.
- При этом `architecture/ta/k8s.yaml` не должен дублировать `policy`/`pam`/`keys` и т.п.: исходящие ссылки задаются внутри `seaf.ta.services.kbs`. Например, `jupiter.kb.9` уже связывается с несколькими `k8s` кластерами как «выходящая связь» — это и есть нормальная модель.
- Поэтому, если `/core/storage/problems/` всё ещё возвращает `items` с `uid=...notfound...`, значит `archtool` не видит соответствующую запись из `seaf.ta.services.kbs` (или она хранится в другом файле). Проверяйте `/entities/seaf.ta.services.kbs/list`, чтобы понять, какие `jupiter.kb.*` реально загружены, и дополняйте их через `.yaml` файлы, которые точно импортируются.
- Правило `seaf.validation.ta.p3.k8s_policy_engine` теперь не ищет поле `policy` в самом кластере, а проверяет `protected_services` у KB-записей `tag=Policy`. Это значит, что достаточно добавить `jupiter.k8s.*` в список `protected_services` соответствующего `jupiter.kb.policy.kyverno` (см. `/entities/seaf.ta.services.kbs/list`), а не изменять `architecture/ta/k8s.yaml`.
