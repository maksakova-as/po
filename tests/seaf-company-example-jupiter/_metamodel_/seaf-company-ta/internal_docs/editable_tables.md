# Editable Tables в Dochub

Этот документ собирает всё, что нужно знать, чтобы проектировать и сопровождать редактируемые таблицы (`type: editable-table`) в репозитории `seaf-company-example-jupiter`. Информация комбинирует официальное описание из `_metamodel_/SEAF1/editable-table-docs/Как-это-работает.md` и практические нюансы, выявленные при настройке таблиц для ЦОДов (`dc_edit_table.yaml`) и сетей (`network_edit_table.yaml`).

## 1. Базовые концепции

Структура документа:

```yaml
docs:
  <doc-id>:
    type: editable-table
    location: /Путь/в/меню
    description: ...
    page_size: 10
    selection: false
    filtration: true
    direction: ltr
    origin: { ... }
    headers: [ ... ]
    source: > (...)
    format: > (...)
```

**Важно:** Инструкции по перезапуску сервера и проверке работоспособности см. в `Docs/operations_manual.md`.

Ключевые поля:

- **origin** — объявляет все JSONata-переменные. **Не добавляйте** `file: seaf.ds.file` в origin, так как это может вызвать ошибку 500 при загрузке; переменная `file` доступна в `format` автоматически.
- **headers** — описание колонок.
- **source** — JSONata для формирования строк таблицы.
- **format** — JSONata для сохранения. **Критично:** должен использовать слияние (`$merge`), а не перезапись.

## 2. Особенности работы с колонками

### 2.1. Редактируемые ячейки

- Ставим `editable: true`.
- В `save` минимум нужен `path` (относительный путь до файла от места расположения документа).

### 2.2. `options` для select/multiple-select

Для списков выбора (`options`) есть два рабочих подхода:
1. **Отдельные датасеты** (Рекомендуемый): Создать отдельный файл `..._options.yaml` с датасетом, подключить его в `origin`, и ссылаться как `options: > (my_options_dataset)`.
2. **Inline JSONata**: Использовать выражение прямо в headers, например:
   ```yaml
   options: >
     (
       $list := ...;
       $map($keys($list), ...)
     )
   ```
   Этот способ работает (как в `storages`), но требует аккуратности.

### 2.3. Массивы в `multiple-select`

UI ждёт массив. В `source` и `format` приводите значения:
```jsonata
$to_array := function($value){ $type($value) = "array" ? $value : ($exists($value) ? [$value] : []) };
```

### 3. Сохранение данных (`format`)

Функция `format` получает `file` (текущий контент). Чтобы не потерять данные других объектов в файле, используйте слияние:

```jsonata
    format: >
      (
        $table := $exists(table) ? table : {};
        $file_data := $lookup(file, "seaf.ta.services.kbs");
        $existing := $exists($file_data) ? $file_data : {};
        $updates := $map($keys($table), ...);
        {
          "seaf.ta.services.kbs": $merge([$existing, $updates])
        }
      )
```

## 4. Распространённые ошибки

| Проблема | Причина | Решение |
| --- | --- | --- |
| 500 Internal Server Error | Ошибка в `origin` (например, `seaf.ds.file`) или некорректный датасет | Убрать лишние переменные из `origin`, проверить `curl` запросом доступность датасета. См. `Docs/operations_manual.md`. |
| Таблица пустая | Ошибка в `source` или пустой датасет | Проверить JSONata в playground. Убедиться, что датасет возвращает данные. |
| После сохранения файл затирается | `format` возвращает только изменённые строки | Использовать `$merge([$existing, $updates])`. |


## 5. Пример: `dc_edit_table.yaml`

- Содержимое YAML в `architecture/ta/dc.yaml` редактируется через таблицу с полями ID, название, описание, vendor, ownership, type, address, rack_qty, tier, availabilityzone, external_id.
- Для сохранения всех строк `format` берёт текущее содержимое файла (`$file_data`), накладывает изменения из таблицы, приводит `rack_qty` к числу и возвращает полный объект `seaf.ta.services.dcs`.
- Путь `../../../architecture/ta/dc.yaml` гарантирует, что изменения попадают в рабочий файл.

## 6. Пример: `network_edit_table.yaml`

- Есть две страницы (LAN и WAN). Обе читают общий датасет `seaf.company.ds.ta.networks`, но фильтруют строки по `type`.
- Для колонок `segment` и `location` используются отдельные датасеты-справочники, чтобы валидатор видел «готовые» `options`.
- В `format` мы сливаем новые значения с текущим YAML, чтобы на вводе/выводе корректно обрабатывались массивы и не исчезали другие записи.
- После разделения на отдельные страницы можно развивать таблицы независимо (например, добавлять поля только для WAN).

## 7. Рекомендации

1. **Всегда проверяйте относительные пути**. Самая частая ошибка — забыть `../..` и писать изменения в `_metamodel_`.
2. **Используйте датасеты для справочников**. Это позволяет переиспользовать списки и удовлетворяет валидатор.
3. **Приводите массивы к нужному типу**. `multiple-select` без массива не работает.
4. **Сохраняйте структуру YAML**. `format` должен возвращать полный объект (особенно когда добавляются строки).
5. **Перезапускайте archtool после изменения документов**. Dochub читает `_metamodel_` только при старте, поэтому любые правки YAML требуют `docker restart` + паузу ~20 секунд.
6. **Документируйте назначения колонок**. Чем подробнее описание (особенно `description` документа), тем проще сопровождать таблицу.

С этими принципами настройка новых редактируемых таблиц проходит значительно быстрее, а ошибок/чёрных экранов становится минимально.
