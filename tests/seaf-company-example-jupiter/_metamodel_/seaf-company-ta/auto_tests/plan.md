# План автоматизированного тестирования Technical Architecture (TA)

Этот документ описывает стратегию и механизмы тестирования наполненности данных и работоспособности веб-интерфейса для домена TA.

## 1. Тестирование наполненности датасетов (Data Completeness)

**Цель:** Гарантировать, что все объекты, описанные в файлах `architecture/ta/*.yaml`, корректно загружаются в озеро данных и попадают в целевые витрины (datasets).

### Механизм
Реализуется набор Python-скриптов для сверки "Источник (файлы) vs Витрина (API)".

1.  **Сканер файловой системы (`scan_yaml_entities.py`)**
    *   **Задача:** Пройти по всем YAML-файлам в папке `architecture/ta/`.
    *   **Логика:** Парсить YAML и искать корневые ключи или объекты внутри, соответствующие паттерну `seaf.company.ta.*`.
    *   **Выход:** Словарь вида `{ "seaf.company.ta.services.backups": 5, "seaf.company.ta.components.servers": 42, ... }`.

2.  **Сборщик метрик датасетов (`fetch_dataset_counts.py`)**
    *   **Задача:** Опросить API ArchTool (`/core/storage/jsonata/`) для получения количества объектов в датасетах.
    *   **Логика:** Использовать существующий список dataset IDs.
    *   **Выход:** Словарь вида `{ "seaf.company.ds.ta.backup": 5, "seaf.company.ds.ta.servers": 40, ... }`.

3.  **Компаратор (`compare_counts.py`)**
    *   **Задача:** Сравнить данные сканера и сборщика.
    *   **Конфигурация:** Карта соответствия (Mapping) "Сущность -> Датасет".
        *   *Пример:* `seaf.company.ta.services.backups` -> `seaf.company.ds.ta.backup`
    *   **Отчет:**
        *   ✅ **OK:** Количество совпадает.
        *   ❌ **Missing:** В файлах больше, чем в датасете (объект не попал в выборку).
        *   ⚠️ **Extra:** В датасете больше, чем в файлах (дубликаты или фантомные объекты).

### Расположение
Скрипты будут размещены в `_metamodel_/seaf-company-ta/auto_tests/completeness_test/`.

## 2. Автоматизированное тестирование веб-интерфейса (UI Testing)

**Цель:** Проверить доступность и корректность отображения меню, списков и карточек объектов в ArchTool.

**Инструмент:** [Playwright](https://playwright.dev/) (Node.js).

### Сценарии тестов

#### А. Навигация и Меню (`tests/menu.spec.js`)
1.  Открыть главную страницу.
2.  Найти пункт меню "Техническая архитектура".
3.  Развернуть меню и проверить наличие подпунктов:
    *   Компоненты (Серверы, СХД, Сеть...)
    *   Сервисы (Инфраструктура, K8s, Окружения...)
4.  **Критерий успеха:** Элементы меню видимы и кликабельны.

#### Б. Содержимое Таблиц (`tests/tables.spec.js`)
1.  Перейти на страницу списка (например, `/entities/seaf.company.ta.services.backups/list`).
2.  Дождаться загрузки таблицы.
3.  Проверить, что количество строк > 0.
4.  Проверить наличие заголовков колонок (Название, Описание и т.д.).
5.  **Критерий успеха:** Таблица рендерится, данные присутствуют.

#### В. Карточки и Виджеты (`tests/cards.spec.js`)
1.  Открыть карточку конкретного объекта (по известному ID, например, K8s кластер).
2.  **Проверка заголовка:** Название объекта соответствует ожидаемому.
3.  **Проверка виджетов:**
    *   Наличие специфичных таблиц (например, "Сетевые интерфейсы").
    *   Наличие PlantUML диаграмм (проверка рендеринга SVG).
4.  **Критерий успеха:** Карточка открывается без ошибок (не 404/500), диаграммы визуализируются.

### Структура проекта UI тестов
`_metamodel_/seaf-company-ta/auto_tests/ui_test/`
*   `package.json` - зависимости (playwright).
*   `playwright.config.js` - настройки (base URL: http://127.0.0.1:8080).
*   `tests/` - файлы спецификаций (*.spec.js).

## План внедрения

1.  Создать структуру каталогов (выполнено).
2.  Написать скрипт `scan_yaml_entities.py` для парсинга архитектуры.
3.  Написать `compare_counts.py` с маппингом сущностей.
4.  Инициализировать Playwright проект в `ui_test`.
5.  Написать базовый тест проверки меню и одной таблицы.
