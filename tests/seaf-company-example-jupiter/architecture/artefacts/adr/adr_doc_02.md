## Описание проблемы
В настоящее время существует высокая степень операционной связанности (operational coupling) между сервисами «Заказы» (OMS) и «Платежи» (Billing). При создании заказа система синхронно вызывает API платежного шлюза. В периоды пиковых нагрузок (распродажи, черная пятница) это приводит к таймаутам, исчерпанию пула соединений в OMS и каскадным отказам. Необходимо устранить жесткую синхронную зависимость, не потеряв гарантии проведения платежа и консистентность данных в распределенной системе.

## Контекст ситуации
- **Цели**: Обеспечить отказоустойчивость (сценарий: Billing недоступен → OMS продолжает принимать заказы), снизить latency для клиента (время ответа API создания заказа не должно зависеть от скорости обработки платежа).
- **Ограничения**:
    - В компании действует политика строгой изоляции доменов.
    - Команда Billing работает в стеке Java (Spring), команда OMS — в стеке C# (.NET).
    - Требование к аудиту: каждое действие по списанию средств должно быть неопровержимо зафиксировано (Event Sourcing на стороне Billing).
    - Текущий SLA: 99.95% доступности OMS; Billing исторически имеет SLA 99.9% из-за зависимости от внешних банковских шлюзов.
- **Существующие обстоятельства**: Инфраструктура поддерживает как синхронные (Kong, Istio), так и асинхронные паттерны (Kafka кластер версии 3.2, управляемый SRE).

## Рассматриваемые варианты

### Вариант 1: Синхронная коммуникация (REST/gRPC) с паттерном Circuit Breaker
Использование Hystrix/Resilience4j с таймаутами и fallback-механизмами.
- **Плюсы**:
    - Простота отладки (request-response трассировка).
    - Ментальная модель "запрос-ответ" привычна для обеих команд.
    - Меньше задержек в идеальном сценарии (без падений).
- **Минусы**:
    - Fallback сценарии сложны (при недоступности Billing мы не можем создать заказ, либо создаем его в статусе "ожидание оплаты", что требует последующего ручного вмешательства или поллинга).
    - Остается проблема *head-of-line blocking*: медленный ответ Billing по одному запросу блокирует поток в OMS.
    - Требует сложной настройки пулов потоков для изоляции.

### Вариант 2: Асинхронная коммуникация через очереди (RabbitMQ / Kafka) + паттерн Saga (Orchestration)
Внедрение оркестратора (сага), который публикует команду `ProcessPayment` в топик. OMS возвращает клиенту `202 Accepted` сразу после валидации заказа. Billing читает команду, выполняет списание, публикует событие `PaymentCompleted`.
- **Плюсы**:
    - **Слабое связывание**: OMS не знает о деталях реализации Billing, знает только о формате события.
    - **Устойчивость**: Если Billing лежит, сообщения накапливаются в очереди (backlog) и обрабатываются позже. OMS продолжает принимать заказы.
    - **Масштабирование**: Легко масштабировать консьюмеров Billing горизонтально, управляя партициями (Kafka).
    - **Аудит**: Лог событий (event log) в Kafka является естественным источником данных для аудита и воспроизведения состояний.
- **Минусы**:
    - **Сложность**: Усложняется отладка цепочек (нужна трассировка correlationId). Внедрение паттерна Saga требует управления компенсирующими транзакциями (отмена заказа при ошибке оплаты).
    - **Косвенная задержка**: Клиент получает подтверждение мгновенно, но статус оплаты приходит асинхронно (нужен WebSocket или поллинг со стороны клиента, либо фронт подписывается на SSE).

### Вариант 3: Гибридный подход (Request-Reply + Event Sourcing)
Синхронный вызов только для инициализации (создание временной блокировки средств), остальное через события.
- **Плюсы**: Сочетает предсказуемость первого ответа с надежностью асинхрона.
- **Минусы**: Удваивает сложность реализации (поддержка двух протоколов) и увеличивает количество точек отказа.

## Принятое решение
**Выбран Вариант 2: Асинхронная коммуникация через Apache Kafka с реализацией паттерна Orchestration-based Saga.**

Архитектурный стиль взаимодействия между доменами (биллинг и заказы) переводится на **событийно-ориентированный**. OMS выступает в роли оркестратора, публикуя команды. Billing выступает в роли обработчика команд и публикатора событий состояний. Для гарантии доставки используется exactly-once semantics (идимпотентность обработки на стороне Billing).

## Обоснование выбора
1.  **Устойчивость к отказам (Failure Isolation)**: Основной критерий. Падение Billing более не приводит к каскадному отказу OMS. Это повышает общий SLA системы с 99.9% (как у самого слабого звена) до 99.95%+ для критического сценария "создание заказа".
2.  **Соответствие стратегии Data Mesh**: Компания движется к Data Mesh, где домены должны обмениваться данными через управляемые события, а не через прямые API. Данный ADR соответствует этой стратегии.
3.  **Неотвратимость аудита**: В отличие от синхронных вызовов, где логи могут потеряться при сбое инфраструктуры, наличие постоянного лога в Kafka (retention 30 дней) гарантирует, что ни один запрос на оплату не будет потерян. Это закрывает требование Compliance.
4.  **Масштабируемость**: Позволяет независимо масштабировать OMS (сеть) и Billing (CPU-интенсивные операции криптографии и интеграции с банками).

## Последствия

### Архитектурные
- **Введение новых паттернов**: В архитектуру вводятся паттерны **Saga** и **Transaction Outbox** (для гарантии атомарности записи в БД OMS и публикации команды в Kafka). Это повышает сложность разработки на 15-20% на старте.
- **Управление состоянием**: OMS теперь должен управлять более сложным жизненным циклом заказа (состояния: `CREATED`, `AWAITING_PAYMENT_CONFIRMATION`, `PAID`, `PAYMENT_FAILED`). Раньше состояние определялось кодом ответа HTTP.
- **API Gateway**: В API Gateway необходимо добавить поддержку асинхронных ответов (SSE или WebSocket), чтобы клиент (мобильное приложение) мог получить итоговый статус платежа без поллинга.

### Процесс разработки
- **Стандарты**: Введен обязательный стандарт: для любого межсервисного взаимодействия в домене высокой критичности сначала должна быть определена схема события (Avro) в реестре схем.
- **Тестирование**: Командам потребуется внедрить инструменты для тестирования асинхронных сценариев (например, тесты-контракты с помощью Pact или Spring Cloud Contract для Kafka). Недостаточно тестировать только REST endpoints.
- **Наблюдаемость**: Обязательное внедрение сквозного `correlationId` (из HTTP заголовка в Kafka headers). Без этого диагностика инцидентов станет невозможной. Требуется доработка дашбордов в Datadog/Kibana для поиска по correlationId.

### Эксплуатация
- **SRE**: Изменяется модель мониторинга. Вместо мониторинга HTTP 5xx для Billing, SRE переходит на мониторинг **lag потребителя** (consumer lag) в Kafka. Lag > 10k за 5 минут — критический алерт.
- **Безопасность**: Необходимо настроить mTLS и ACL на уровне Kafka, так как данные о платежах относятся к категории критических (PCI DSS). Ранее безопасность обеспечивалась на уровне сетевых политик (mTLS в сервисной сетке).
