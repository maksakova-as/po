# План оптимизации датасетов TA

Документ фиксирует практический план работ по оптимизации датасетов в модуле `seaf-company-ta` без изменения бизнес-результата.

## 1. Цель и критерии успеха

Цель:
- Снизить время вычисления тяжелых датасетов TA.
- Уменьшить количество повторных вычислений при открытии карточек и схем.
- Снизить риск рассинхронизации логики маппинга между разными датасетами.

Критерии успеха:
- `seaf.company.ds.ta.schema_r41_reverse_compat` ускорен минимум на 25%.
- `seaf.company.ds.ta.servers` и `seaf.company.ds.ta.network_components` ускорены минимум на 20%.
- Нет функциональных регрессий по карточкам и схемам R41.
- Все изменения покрыты smoke-проверками датасетов.

## 2. Базовые метрики (замер перед стартом)

Перед началом каждой фазы выполнить baseline-замер:
1. Время ответа `/core/storage/jsonata` для:
- `seaf.company.ds.ta.networks`
- `seaf.company.ds.ta.servers`
- `seaf.company.ds.ta.network_components`
- `seaf.company.ds.ta.schema_r41_reverse`
- `seaf.company.ds.ta.schema_r41_reverse_compat`
2. Размер payload каждого датасета.
3. Время `storage/reload` и warmup.

Формат фиксации:
- Таблица в `internal_docs/datasets_ta.md` или отдельный лог-файл в `internal_docs/`.
- Для каждого датасета хранить минимум: `dataset`, `ms`, `payload_len`, `date`, `commit`.

## 3. Порядок выполнения

## Фаза A. Снижение повторных вычислений reverse-источников

Задача:
- Убрать многократные `$eval` одних и тех же reverse-датасетов в `ta/datasets.yaml`.

Шаги:
1. Ввести промежуточные датасеты-кэши в `ta/datasets.yaml`:
- `seaf.company.ds.ta.reverse.cache.core`
- `seaf.company.ds.ta.reverse.cache.network`
- `seaf.company.ds.ta.reverse.cache.platform`
2. Внутри кэшей один раз вычислить наборы reverse:
- cloud + vmware dcs
- cloud + vmware networks/segments
- cloud + vmware servers
- network_components + nat + vpn + elb + vmware components
3. В целевых датасетах TA заменить прямые `$eval(datasets....source, $ctx)` на `origin`-ссылки к кэшам.
4. Проверить что merge/dedupe логика не поменялась семантически.

Проверки:
1. Сравнить count объектов до/после по основным датасетам.
2. Прогнать ключевые карточки:
- сервер
- сеть
- сетевое устройство
3. Прогнать R41 reverse и проверить отсутствие новых ошибок в plugin.log.

Ожидаемый эффект:
- Уменьшение CPU на повторных открытиях UI.
- Стабилизация времени ответа для тяжелых TA-датасетов.

## Фаза B. Оптимизация VMware reverse серверов

Задача:
- Ускорить `reverse2seaf2.ds.ta.reverse.vmware.servers`.

Шаги:
1. В `reverse/ta/dataset_parts/vmware_onprem/vmware_servers.yaml` заменить lookup сети по title:
- Сейчас: перебор `$networks.$spread()` при каждом запросе.
- Нужно: построить индекс `title -> network_id` один раз.
2. Для поиска сетей использовать индекс вместо полного прохода.
3. Проверить, что fallback по `subnets` и host `portgroups` сохраняет прежний результат.

Проверки:
1. Точечно сверить `subnets` для набора контрольных VM.
2. Проверить отсутствие missing network refs в `seaf.company.ds.ta.servers`.
3. Проверить время ответа `reverse2seaf2.ds.ta.reverse.vmware.servers`.

Ожидаемый эффект:
- Снижение времени построения VMware reverse servers.

## Фаза C. Облегчение `schema_r41_reverse_compat`

Задача:
- Убрать избыточную глобальную рекурсивную нормализацию в `_extensions/ta_docs/r41/datasets/root.yaml`.

Шаги:
1. В `seaf.company.ds.ta.schema_r41_reverse_compat` ограничить нормализацию только нужными коллекциями:
- `seaf.ta.components.network`
- `seaf.ta.components.server`
- `seaf.ta.components.hw_storage`
- `seaf.ta.components.user_device`
2. Ограничить поле-нормализацию только для:
- `network_connection`
- `network_links`
- `isp`
- `segment`
3. Убрать полную рекурсию `$sanitize_nulls` для всех веток, оставить targeted sanitation только для полей, критичных плагину.

Проверки:
1. Проверить, что схемы R41 reverse открываются без ошибок.
2. Сравнить структуру output до/после на контрольных ключах.
3. Сравнить время и размер payload.

Ожидаемый эффект:
- Наибольшее ускорение среди пользовательских диаграммных датасетов.

## Фаза D. Централизация маппингов

Задача:
- Убрать дублирование правил маппинга типов.

Шаги:
1. Создать служебный датасет:
- `seaf.company.ds.ta.meta.registry`
2. Перенести туда:
- маппинг сетевых component-type
- маппинг Kadzo class -> SEAF service_type
- map plural->singular для R41 где применимо
3. В `_extensions/kadzo/datasets/dataset_parts/*.yaml`, `_extensions/ta_docs/r41/datasets/root.yaml`, `ta/datasets.yaml` заменить hardcoded map на `$lookup` из registry.

Проверки:
1. Сравнить итоговые `service_type` и `__object_type` по выборке объектов.
2. Прогнать карточки и R41.

Ожидаемый эффект:
- Ниже риск регрессий при будущих изменениях справочников.

## Фаза E. Снижение зависимости карточек от all_objects

Задача:
- Минимизировать использование тяжелого `seaf.company.ds.ta.all_objects` для точечных карточек.

Шаги:
1. Для карточек `presentations/*.yaml` заменить `origin: all_objects` на таргетные датасеты там, где это возможно.
2. Оставить fallback в `all_objects` только при реальном отсутствии в целевом датасете.
3. Проверить функцию объединения виджетов, чтобы fallback вызывался лениво.

Проверки:
1. Время открытия карточки сервера, сети, сетевого устройства.
2. Отсутствие потери полей в карточках.

Ожидаемый эффект:
- Быстрее first render карточек.

## Фаза F. Перф-тесты и guardrails

Задача:
- Зафиксировать автоматические проверки производительности.

Шаги:
1. Добавить скрипт в `auto_tests` для замера latency основных датасетов.
2. Ввести пороги предупреждений по времени.
3. Добавить markdown-отчет в результаты test-run.

Проверки:
1. Скрипт отрабатывает локально и в CI.
2. Пороговые превышения видны как warning/error.

Ожидаемый эффект:
- Раннее обнаружение деградаций.

## 4. Стратегия внедрения

Порядок merge:
1. Фаза A
2. Фаза B
3. Фаза C
4. Фаза D
5. Фаза E
6. Фаза F

Правило релиза:
- Каждая фаза отдельным PR.
- После каждого PR фиксируется таблица `до/после` по метрикам.
- Переход к следующей фазе только при отсутствии функциональных регрессий.

## 5. Риски и контроль

Риски:
1. Скрытая зависимость UI/плагина от текущей структуры полей.
2. Изменение порядка merge источников может изменить финальные ID.
3. Перекрестные эффекты между reverse и seaf1 dedupe.

Контроль:
1. Обязательная выборочная сверка ключевых объектов по ID.
2. Проверка plugin.log после каждой фазы.
3. Набор smoke-сценариев по карточкам и R41.

## 6. Definition of Done по оптимизации

Оптимизация считается завершенной, когда:
1. Пройдены все фазы A-F.
2. Время `schema_r41_reverse_compat` уменьшено минимум на 25%.
3. Время `servers` и `network_components` уменьшено минимум на 20%.
4. Нет новых ошибок в plugin.log по схемам TA.
5. Документация и тесты обновлены.
