# Реальная карта преобразования реверса → SEAF2

Эта карта отражает, какие сущности из `_metamodel_/SEAF1/iaas/adv_reverse2seaf` (см. `mapping_analysis.md` и `modules/*_converter.py`) мы будем использовать, какие промежуточные датасеты создаём в `reverse2seaf2` и в какие сущности SEAF2 они попадут:

| Источник (reverse/metamodel) | Нужный датасет в `reverse2seaf2` | Целевая сущность SEAF2 | Что мапим/как трансформируем |
|------------------------------|-------------------------------|------------------------|---------------------------|
| `seaf.ta.reverse.cloud_ru.advanced.vpcs` (входные VPC + подсети, модуль `vpcs_converter`) | `reverse_network_devices` — из каждой VPC делаем “маршрутизатор” (`router`) и сохраняем `network_connection`, `segment`, `location`, `description`, `external_id`. | `seaf.ta.components.network` (связь с `seaf.company.ta.components.servers`) и `seaf.company.ta.components.servers` (через `reverse_servers` merge) | Преобразуем `id` → `__id__`, `name` → `title`, `cidr`/`description` → поля описания, `tenant` → `__company_id__`, `segment_ref` → `segment`, `dc` → `location`, `link`/`source_key` → `__link_to_card__`, `resource_id`. |
| `seaf.ta.reverse.cloud_ru.advanced.cces`, `rdss`, `dmss`, `ecss` (модули `cces_converter`, `rdss_converter`, `dmss_converter`, `ecss_converter`) | `reverse_clusters` — агрегируем по кластерам (CCE/DB) и добавляем виртуальные/metal-ноды в `reverse_servers`. | `seaf.company.ta.services.cluster_virtualizations`, `seaf.company.ta.components.servers` | Поля `name/alias` → `title`, `available_az/location` → `location`, `tenant` → `__company_id__`, `network_connection/subnet_id` → сети, `service_type` → `type`, `link` → `__link_to_card__`. |
| `seaf.ta.reverse.cloud_ru.advanced.vpn_connections` + `vpn_gateways` | `reverse_network_links` — строим связи/сетевые объекты, которые можно объединить с datalist для сетей. | `seaf.company.ta.services.network_links`, `seaf.company.ta.services.networks` | `source_vpc/accept_vpc` → `network_connection`, `remote_subnets` → `segment`, `tenant` → `__company_id__`, `DC` → `location`, `description` → `title`. |
| `seaf.ta.reverse.general.data` (общее `data_lake`, см. `seaf.ds.objects`) | `reverse_objects` (вспомогательный dataset) — превращаем роутеры/кластеры реверса в объекты `seaf.ds.objects`, но только для merge-ов в конкретных представлениях. | `seaf.company.ta.components.servers`, `cluster_virtualizations`, `network_links` | Формируем `__entity_id__`/`__link_to_card__`, а также `is_part_of`, `virtualization`, `availabilityzone` и другие поля, чтобы downstream view могли взять эти объекты по привычным путям (`objects."seaf.company.ta.components.servers"`). |

**План действий**
1. На базе `vpcs_converter`, `cces_converter`, `rdss_converter` и прочих модулей (`seaf-company-example-jupiter/_metamodel_/SEAF1/iaas/adv_reverse2seaf/modules/*_converter.py`) собрать дополнительные датасеты `reverse_network_devices`, `reverse_clusters`, `reverse_network_links` (описанное выше). Они читают `data_lake` (то есть `seaf.ta.reverse.*`).  
2. В нужных SEAF2-датасетах (`seaf.company.ds.ta.servers`, `cluster_virtualizations`, `network_links`, `reverse_vpcs/presentations`) добавить merge/origin, который объединяет основное содержимое (из `seaf.ds.objects` и `seaf.ds.objects_by_entities`) с `reverse_*`.  
3. Перед перезапуском контейнера проверять (`curl /core/storage/jsonata/…`) корректность новых датасетов, чтобы потом UI сразу сделал merge.  

Такой подход сохраняет изоляцию `reverse2seaf2`, но делает реверсные объекты доступными и для обычных таблиц (серверов, кластеров, сетей) через прозрачные merge-ы, опирающиеся на данные из `adv_reverse2seaf`.
